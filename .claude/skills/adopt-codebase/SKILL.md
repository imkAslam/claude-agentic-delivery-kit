# Adopt codebase

A new project is designed first and built second. An existing codebase is the other way round: **the code is the truth, and the documents describe it.** Adopt mode writes the smallest set of accurate documents the kit needs to work safely, records what is already wrong without fixing it, and asks the human for one baseline approval. After that, every change goes through the normal workflow.

## When to Use
- **Orchestrator:** lane `adopt` in `.claude/skills/deliver/references/workflow.md` (after `delivery-state.sh init --mode adopt`)
- **Every agent with `MODE: adopt` in its brief:** the rules in [AS_BUILT_RULES.md](references/AS_BUILT_RULES.md) and its row in the table below
- **quality-security-agent:** the baseline checks and [BASELINE_TEMPLATE.md](references/BASELINE_TEMPLATE.md)
- **qa-agent:** [TEST_INVENTORY_TEMPLATE.md](references/TEST_INVENTORY_TEMPLATE.md)
- **Engineers and reviewers after the baseline:** "Working in adopted code" below

## Instructions

### Step 0: Preconditions (orchestrator)
- The repository has product code and **no** delivery run. A run that exists is never converted.
- The working tree is clean (the human commits or stashes their work first): the baseline is tied to a commit.
- Scope: the whole repository, or the folders the human named. Folders outside the scope stay **unmapped**: no role owns them, so role agents cannot edit them until they are adopted (a later baseline extension through a change request).
- Until the baseline is approved, only documents, the kit and contracts are written (`guard-coding.sh`). Tell the human that coding in this repository through Claude Code is paused until then.

### Step 1: Who writes what (all documents-only, all as built)
| Step | Agent | Reads | Writes |
|---|---|---|---|
| `detect` | system-detector | The tree, manifests, lockfiles, CI config, container files | `SYSTEM-PROFILE.md` with an **Existing code** section: languages and frameworks with versions, package manager, test runner and tools, CI, migrations tool, existing API specs, theme or token source, UI library, size per top-level folder (files, lines), and for each candidate command whether it ran green |
| `map` | solution-architect | SYSTEM-PROFILE, entry points, module folders, config | `.claude/project.json` (roles enabled for what exists; `paths` from the real folders with no overlap; `shared_files`; `commands` that were run and passed; `guides` for the real stack), `.claude/PROJECT.md`, `ARCHITECTURE.md` as built, the derivable diagrams in the PRD (then `sync-diagrams.sh`), ADRs for inherited decisions |
| `as-built-fork` | database-architect | Migrations and schema or ORM files (never a remote database) | `DATA-MODEL.md`: tables, keys, constraints, indexes, relationships, personal-data columns; the D6-erd source to the architect |
| | api-designer | Route definitions, controllers, an existing API spec | Contracts in `contracts.paths`: the existing spec if there is one; else generated by the framework's own tool; else written from the routes. State the coverage (operations documented ÷ operations found) |
| | ba-agent, then product-manager | Routes and screens, auth and role code, tests, README and existing docs | `BA-ANALYSIS.md` (roles and permissions, entities, journeys found) and a **light `PRD.md`**: product summary, personas from the roles, feature list `F-…` with status *built*, the main journeys, business rules cited to code, NFRs that can be observed. | | qa-agent | Test folders, test config, CI | `TEST-INVENTORY.md` |

| `baseline-checks` | quality-security-agent | `project.json` commands, the tree | `BASELINE.md` (Step 2) |
| `as-built-docs` | docs-writer | The documents above, the tree | `docs/README.md`, `FEATURES.md` (every existing feature, status *built*), `database/DATABASE.md`, `SYSTEM-FLOWS.md` for the main journeys, `CODEMAP.md` |
| `as-built-review` | architect-reviewer | Everything above + the code | The accuracy review (Step 3) |

Depth is a **working baseline**: enough for agents to find code, respect boundaries and review changes. Do not write acceptance criteria, mockups or component specs for everything that exists; they are written later for the areas a change touches ("deepen on touch").

### Step 2: Baseline checks and the debt register
The quality-security-agent runs, and records with exit codes and output summaries: every `project.json` command (lint, typecheck, test, build), `check-hygiene.sh` on the whole tree, the dependency audit, the secret scan, `check-migrations.sh` (if there are migrations), `check-tokens.sh` (if tokens were extracted), and collects the debts the other agents reported (architecture deviations, missing tests, security gaps, missing contracts). It writes `docs/delivery/BASELINE.md` with [BASELINE_TEMPLATE.md](references/BASELINE_TEMPLATE.md).

**Commands must end green.** The commit gate runs them on every commit, so a red command would block all future work. When an existing command fails:
1. Record the failure in the debt register with its evidence.
2. Propose the smallest honest fix to the architect: a command scoped to what passes, or the project's own quarantine mechanism for the named failing tests, each with its debt id.
3. The quarantine is a **risk the human accepts at the gate**; it is listed there by name and is never applied silently.

### Step 3: Accuracy review
The architect-reviewer samples at least 10 claims per document (or all, if fewer) and checks each against the code: the path exists, the table has those columns, the operation is routed, the rule is in the cited lines. It also runs `check-diagrams.sh --mirror`, checks that role paths don't overlap and that every command in `project.json` was run. A claim without a citation, or one the code contradicts, is P2 (P1 for boundaries, commands and security claims). Loop id `as-built-review`, the usual round cap.

### Step 4: The baseline gate
Present it with the `gate-review` skill (`gates.md` → `baseline`). At most 5 business questions, each with a recommended default:
1. Is the product summary and the feature list right, and is anything listed that should be retired?
2. Which **P1 debts** get a "fix now" ticket before new work, and which risks are accepted for now?
3. The quarantined checks, if any: accept until fixed?
4. Business facts the code can't tell (who the users are, retention, uptime and performance targets).
5. The scope: whole repository, or which folders stay unmapped.

On approval, commit the package, then:
```bash
bash .claude/skills/deliver/scripts/delivery-state.sh approve-baseline "<approver>" "<notes>" \
  docs/delivery/PRD.md docs/delivery/ARCHITECTURE.md docs/delivery/BASELINE.md docs/delivery/DATA-MODEL.md <contracts path> <the other as-built documents>
```
It records `baseline`, `g1` and `g2` together, tags the commit `delivery-baseline`, and moves the run to `build / increment-wait`. Register the "fix now" debts as tickets (`ticket add … --type chore`).

### Step 5: After the baseline (increments)
New work arrives as evidence in `docs/intake/`. Follow `workflow.md` → "Increments": discovery for the change only, a change request the human approves, then plan, build, verify and release as for a new product.

## Working in adopted code (engineers and reviewers)
- **Read `docs/CODEMAP.md` first,** then the as-built documents for the area you touch. Follow the conventions the codebase already has (engineering principle 15), even where the kit's defaults differ.
- **Deepen on touch:** the ticket's discovery adds the acceptance criteria, contract detail and design detail for the area it changes. If your ticket touches behavior no document describes, report it; don't guess.
- **Characterization tests first:** before changing code that has no tests, write tests that pin its current behavior (they pass on the old code), then make the change test-first (`tdd` skill).
- **Standards apply to what you add or change.** Leave the code you touch a little better; refactor beyond the ticket only through a ticket. Reviewers review the diff, and `check-hygiene.sh` runs with `--base delivery-baseline`.
- **Debt you find** that isn't in the register is a `finding` for the orchestrator, which adds it. Never fix unrelated debt inside a feature ticket.
- **No forced restructuring:** the existing structure, stack and UI library are the baseline. Moving to the kit's defaults is a change the human asks for.

## Rules
- Follow [AS_BUILT_RULES.md](references/AS_BUILT_RULES.md): cite everything, invent nothing, mark the unknown.
- Never change product code, configuration or tests during lane `adopt`. Problems are recorded, not fixed.
- Never read or print secret values; never connect to remote databases or environments to inspect them.
- P1 debt (a secret in the repository, an exploitable hole, a data-loss path) is reported to the orchestrator **immediately**, not at the gate (decision policy: major decisions).
- Stay inside the scope and the profile's budget: read entry points and the code map first, sample large modules, and say what was not read.

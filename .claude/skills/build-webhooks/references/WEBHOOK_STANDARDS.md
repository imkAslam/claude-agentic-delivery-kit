# Webhook standards

## 1. Receiving (a provider calls us)
1. **One endpoint per provider:** `POST /webhooks/<provider>`. No session, no CSRF check, but always signature verification. Body size limit (for example 1 MB) and a rate limit per source.
2. **Verify over the raw body.** Read the exact bytes before any parser. Compute the provider's signature (§3) and compare in constant time. Reject with 400 or 401 and log provider, reason and request id (never the secret or the signature).
3. **Reject stale requests.** When the scheme signs a timestamp, refuse anything older or newer than about 5 minutes. This stops replays of a captured request.
4. **Deduplicate.** Insert the provider's event id into `webhook_events` (unique on provider + event id). If it already exists, return 2xx and stop. Providers deliver at least once; duplicates are normal.
5. **Acknowledge fast.** Store the event and return 2xx well inside the provider's timeout (often 5–10 seconds). All real work happens in a background job. A slow or failing handler makes the provider retry and can get the endpoint disabled.
6. **Process idempotently.** The job may run more than once. Use the event id or a business key to make each effect happen once.
7. **Do not trust the payload when it matters.** For money, status and permissions, fetch the current object from the provider's API. A payload proves that something happened, not what the state is now.
8. **Expect any order.** Events can arrive late or out of sequence. Compare the object's version or timestamp and ignore an older state.
9. **Unknown event types** are stored and acknowledged, then ignored by the job (providers add types over time).
10. **Secrets:** one per provider and environment, by environment-variable name; accept two secrets during rotation.

## 2. Sending (we call subscribers)
1. **Subscriptions:** URL, event types, a per-subscriber secret (generated by us, shown once), an active flag and a failure counter.
2. **URL safety (SSRF):** HTTPS only. Resolve the host and block private, loopback, link-local and metadata addresses, when the subscription is saved **and before every delivery** (DNS can change). Do not follow redirects.
3. **Event envelope:** `{ id, type, version, occurredAt, data }`. The type is versioned (`order.paid.v1`); add fields freely, never change a field's meaning. Send only what the subscriber is allowed to see.
4. **Outbox:** write the event in the same database transaction as the change that caused it. A relay turns outbox rows into deliveries. An event is never sent for a change that rolled back, and never lost when the app crashes.
5. **Signature:** the Standard Webhooks scheme: headers `webhook-id`, `webhook-timestamp` (Unix seconds) and `webhook-signature: v1,<base64 HMAC-SHA256(secret, id + "." + timestamp + "." + body)>`. Several signatures separated by spaces during secret rotation. Document the verification steps for subscribers.
6. **Delivery:** from a queue worker, timeout about 10 seconds. A 2xx is success; anything else is a failure.
7. **Retries:** exponential backoff with jitter over about 24 hours (for example 1 min, 5 min, 30 min, 2 h, 6 h, 12 h). Then a dead letter. After repeated dead letters, disable the subscription and notify its owner.
8. **Delivery log:** every attempt with time, status code, latency and the response's first bytes. Subscribers and admins can see it and trigger a redelivery.
9. **Ordering is not guaranteed;** say so in the documentation. Subscribers deduplicate by `id`.

## 3. Provider signature schemes
Use the provider's official SDK verifier when there is one. Confirm the scheme in the provider's current documentation before implementing; providers change headers and add versions.

| Provider | Header | Scheme | Encoding | Replay protection |
|---|---|---|---|---|
| Stripe | `Stripe-Signature: t=…,v1=…` | HMAC-SHA256 of `t + "." + raw body` with the endpoint secret | hex | Timestamp `t`, 5 minutes by default |
| GitHub | `X-Hub-Signature-256: sha256=…` | HMAC-SHA256 of the raw body | hex (strip the `sha256=` prefix) | Delivery id `X-GitHub-Delivery` for deduplication |
| Shopify | `X-Shopify-Hmac-Sha256` | HMAC-SHA256 of the raw body with the app's client secret | base64 | Event id header for deduplication |
| Slack | `X-Slack-Signature: v0=…` + `X-Slack-Request-Timestamp` | HMAC-SHA256 of `"v0:" + timestamp + ":" + raw body` | hex | Timestamp, 5 minutes |
| Standard Webhooks (many newer providers) | `webhook-id`, `webhook-timestamp`, `webhook-signature: v1,…` | HMAC-SHA256 of `id + "." + timestamp + "." + raw body`; the key is the base64-decoded secret after its `whsec_` prefix | base64 | Timestamp, 5 minutes |
| Twilio | `X-Twilio-Signature` | An HMAC over the full URL plus the sorted form parameters with the auth token. **Sources disagree on SHA-1 vs SHA-256: confirm in Twilio's documentation and use its SDK validator** | base64 | — |
| Providers using asymmetric keys (for example some email and payment providers) | A signature plus a timestamp or certificate header | Verify with the provider's public key or its verification API | — | Timestamp |

Two mistakes cause most failures: verifying the re-serialized JSON instead of the raw bytes, and comparing hex with base64.

## 4. Tables
```text
webhook_events        id · provider · event_id · type · payload (raw text) · received_at · processed_at · status (received | processed | failed | ignored) · error · attempts
                      UNIQUE (provider, event_id) · index on (status, received_at)
webhook_subscriptions id · owner_id · url · event_types · secret_ref (encrypted or a secret-store key, never plain) · active · failure_count · created_at
webhook_deliveries    id · subscription_id · event_id · attempt · status_code · latency_ms · next_attempt_at · status (pending | delivered | failed | dead) · response_excerpt · created_at
                      index on (status, next_attempt_at)
```
Payloads can contain personal data: classify them in DATA-MODEL and delete old rows on a schedule (for example 30–90 days).

## 5. Contracts
- **Outbound events** live in the API contract (OpenAPI 3.1 `webhooks:`), one entry per event type with its payload schema, plus a section for the signature headers and the retry policy. They are versioned and frozen at G2 like operations.
- **Inbound events** are typed in the provider's adapter (only the fields the product uses), validated after signature verification.
- Every event the product emits appears in `docs/SYSTEM-FLOWS.md` under the flow that causes it.

## 6. Test matrix
| Case | Expected |
|---|---|
| Valid signature, new event | 2xx; one row stored; one job queued; the effect happens once |
| Wrong signature / missing header | 400/401; nothing stored; a warning logged |
| Valid signature over a modified body | Rejected |
| Timestamp older than the tolerance | Rejected |
| The same event delivered twice | 2xx both times; one effect |
| Events out of order (older state after newer) | The newer state stays |
| Unknown event type | 2xx; stored; ignored |
| Body over the size limit | 413; nothing stored |
| The job fails midway, then is retried | No double effect |
| Outbound: subscriber returns 500, then 200 | Retried with backoff; delivered; two attempts logged |
| Outbound: subscriber never answers | Timeout; retries; dead letter; subscription disabled at the limit |
| Outbound: URL resolves to a private address | Refused; never called |
| Outbound: signature | A subscriber following the documented steps verifies it |
| Secret rotation | Old and new secrets both accepted during the overlap |

## 7. Operations
- **Logs:** provider, event type, event id, outcome, latency, request id. No secrets, no signatures, no full payloads with personal data.
- **Metrics:** received, rejected (by reason), processed, failed, queue depth and age; delivery success rate and attempts.
- **Alerts:** a spike in signature failures (an attack, or a rotated secret), a growing backlog, a subscription disabled.
- **Rotation:** add the new secret, accept both, switch the provider, remove the old one. Written in `ARCHITECTURE.md › Operations`.
- **Local development:** fixture requests signed with a development secret, or the provider's CLI forwarding sandbox events. Never open a development machine to the internet without the human's approval.

## Review checklist
- [ ] The handler verifies over the raw body, in constant time, before doing anything else; stale timestamps are rejected.
- [ ] Events are stored once (unique provider + event id); duplicates return 2xx.
- [ ] The handler only verifies, records, enqueues and answers; processing is a background job and idempotent.
- [ ] Money, status and permissions are confirmed with the provider's API; out-of-order events are handled.
- [ ] Outbound: signed, queued through an outbox, retried with backoff, dead-lettered, logged, redeliverable.
- [ ] Subscriber URLs are checked against private addresses on save and on every delivery; no redirects.
- [ ] Secrets by name, rotation supported, nothing sensitive in logs.
- [ ] Events are in the contracts and versioned; the test matrix is covered.
